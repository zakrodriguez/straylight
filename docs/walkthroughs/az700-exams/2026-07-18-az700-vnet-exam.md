### Case study — Contoso batch tier (Q39–Q43)

Contoso runs the module's estate and wants to extend it. The deployed
topology:

```
                    vnet-hub 10.100.0.0/22
                    +---------------------------------------+
                    | GatewaySubnet  10.100.0.0/27  (empty) |
                    | snet-dns       10.100.1.0/24          |
                    | snet-shared    10.100.2.0/24          |
                    |   vm-fw1 (NVA, private IP 10.100.2.4) |
                    +---------------------------------------+
                       /                       \
                Connected                   Connected
                     /                           \
   vnet-spoke1 10.101.0.0/24         vnet-spoke2 10.102.0.0/24
   snet-workload [vm-app1]           snet-workload [vm-db1]

   (elsewhere, standalone:  vnet-nat 10.103.1.0/24)
```

Requirements:

- **R1** — a new `vnet-spoke3` for a 60-VM batch tier, in one subnet,
  addressed from the `10.100.0.0/14` pool without colliding with
  anything above.
- **R2** — spoke3 joins the hub-and-spoke.
- **R3** — all spoke1 → spoke2 traffic must pass through `vm-fw1`.
- **R4** — spoke3's VMs need outbound internet only, no inbound; its
  subnet is created with `defaultOutboundAccess: false`.

### Section 1

**Q1.** **d)** 59. Azure reserves 5 addresses in every subnet:
64 − 5 = 59.

**Q2.** /29 → 3 · /28 → 11 · /26 → 59 · /24 → 251 (formula:
2^(32−prefix) − 5). First assignable in `10.103.0.0/26` is
`10.103.0.4` — .0 network, .1 gateway, .2/.3 DNS are all reserved.

**Q3.** The network address (first), the last address (broadcast), and
the first three usable ones: `.1` the subnet's default gateway, `.2` and
`.3` the Azure DNS mapping.

**Q4.** **b)** `GatewaySubnet`. It is a reserved *name*, not a
convention — the gateway will not deploy into any other subnet name.

**Q5.** `GatewaySubnet` → hard minimum /29, recommended /27, must not
carry an NSG · `AzureBastionSubnet` → minimum /26, enforced when the
service (Bastion) deploys · `RouteServerSubnet` → minimum /27.

**Q6.** **c)** `NetcfgSubnetRangesOverlap`. Read the error code, not the
message text — the text shifts across az CLI versions.

**Q7.** The two VNets can never be peered or otherwise connected — the
overlap is legal at creation but poisons every future connectivity
option. The prevention is pre-planning: the track draws every VNet from
one `10.100.0.0/14` pool so no two prefixes can collide.

**Q8.** `az network vnet check-ip-address --resource-group <rg>
--name <vnet> --ip-address <ip>`, reading the `available` property
(`true`/`false`).

**Q9.** **b)** /27. Add the five reserved addresses first: 25 + 5 = 30,
which fits a 32-address /27 (27 usable ≥ 25). A /28 yields only 11
usable.

### Section 2

**Q10.** Two unidirectional resources, each living inside the VNet it
points *from* (`hub-to-spoke1` in `vnet-hub`, `spoke1-to-hub` in
`vnet-spoke1`). Traffic flows only when both exist and both report
`Connected`.

**Q11.** **b)** `Initiated` is the waiting state: this side is
configured, the reverse resource does not exist, and no traffic flows.
The fix is always the same — create the missing direction; the existing
side flips to `Connected` without being touched.

**Q12.** `allowVirtualNetworkAccess` → permits traffic between the
peered VNets at all · `allowForwardedTraffic` → accepts packets the
remote VNet forwarded rather than originated ·
`allowGatewayTransit` → offers this side's VPN/ExpressRoute gateway to
the remote VNet · `useRemoteGateways` → consumes the remote side's
gateway instead of deploying one locally.

**Q13.** **b)** One route for the hub's entire address space,
10.100.0.0/22, next hop type `VNetPeering` (its *source* reads
`Default` — effective-route sources are only `Default`, `User`, and
`VirtualNetworkGateway`). Peering programs the remote VNet's *address
space*, not per-subnet routes, and it lands immediately — no reboot.

**Q14.** **b)** Peering is non-transitive: spoke1 learned the hub's
prefix and nothing beyond it. 10.102.0.0/24 falls through to the
RFC 1918 → `None` system route and the packet is silently dropped.
Nothing in the hub forwards between spokes — there is no router VM and
no gateway.

**Q15.** It permits packets the remote VNet *forwarded* (rather than
originated) to arrive across the peering. It does **not** create any
routes, and it does **not** forward any traffic itself — with the flag
set and nothing else, spoke-to-spoke traffic still drops.

**Q16.** (1) Direct spoke-to-spoke peering — simplest, but a full mesh
needs **n(n−1)/2** peerings; (2) an NVA in the hub plus UDRs in each
spoke pointing spoke prefixes at it; (3) a hub gateway with gateway
transit (`allowGatewayTransit` / `useRemoteGateways`).

**Q17.** **c)** Never both on the same side: one side offers a gateway
(`allowGatewayTransit`, the hub), the other uses it
(`useRemoteGateways`, the spoke).

**Q18.** 10.101.0.0/24 → VirtualNetwork (delivered inside the VNet;
effective-route output calls this next-hop type `VnetLocal`) ·
0.0.0.0/0 → Internet · RFC 1918 ranges → None — silently dropped, so
private traffic never leaks out the Internet path.

### Section 3

**Q19.** The /24 system route. Azure matches on longest prefix first,
always; source precedence (User > BGP > System) only breaks ties between
routes of the *same* prefix length. Precedence never overrides prefix
length — a /24 system route beats a /16 UDR.

**Q20.** `VnetLocal` → stay inside the VNet, delivered directly ·
`VNetPeering` → cross a peering · `Internet` → out Azure's edge ·
`VirtualAppliance` → forward to a specific IP · `VirtualNetworkGateway`
→ into a VPN/ExpressRoute tunnel · `None` → drop the packet (black-hole
route).

**Q21.** **c)** User > BGP > System.

**Q22.** **d)** `VirtualAppliance`. `--next-hop-ip-address` is required
with it and rejected with every other type — an exam answer pairing a
next-hop IP with `Internet`, `None`, or `VirtualNetworkGateway` is wrong
on syntax alone.

**Q23.** Fabric half: `enableIPForwarding` on the NVA's **NIC** (a NIC
property — not a VM property, not an OS setting); without it the fabric
drops packets not addressed to that NIC before the VM ever sees them.
OS half: `net.ipv4.ip_forward=1` on Linux; without it the kernel drops
the forwarded packets the fabric now delivers. Both are required.

**Q24.** **c)** The UDR stays, but the effective route flips to state
`Invalid` and traffic to its prefix black-holes — while every `az`
resource still shows `Succeeded`. The effective route table is the only
place this failure is visible.

**Q25.** `az network nic show-effective-route-table`. Sources: `Default`
(system routes), `User` (UDRs), `VirtualNetworkGateway` (BGP-learned).

**Q26.** The whole subnet: a route table applies to every NIC in the
subnet it is associated with, so all 40 VMs silently lose direct
internet access (forced tunneling), including paths PaaS agents and
extensions depend on. Diagnosed in the effective route table — the
`User`-source 0.0.0.0/0 route overrides the system internet route.

**Q27.** A route table is a standalone resource; it does nothing until
associated with a subnet. The association is a subnet property: one
table per subnet at most, one table reusable across many subnets. A UDR
takes effect the moment its table is associated — live on every NIC in
the subnet immediately, no reboot.

### Section 4

**Q28.** **b)** The implicit default outbound SNAT — the shared, unowned
public address VMs historically fell back to when nothing else provided
a path out. Microsoft announced its retirement for newly created
subnets in September 2025; new designs must use an explicit method.

**Q29.** **c)** NAT gateway — the recommended default for subnet-level
outbound.

**Q30.** One VM, inbound needed anyway → instance-level public IP ·
Standard LB already fronting the pool → load-balancer outbound rules ·
many VMs, outbound-only, SNAT scale → NAT gateway · relying on the
implicit shared SNAT → nothing, that behavior is retired for new
subnets.

**Q31.** `run-command` travels through the Azure control plane to the VM
agent — it never touches the VNet's data plane. Its success therefore
proves nothing about network reachability, NSGs, or routes; the exam
uses it as a distractor for exactly that reason.

**Q32.** **c)** Standard SKU public IPs or public IP prefixes only.
Basic is not accepted.

**Q33.** Maximum addresses: **16** · SNAT ports per address: **~64,000**
· idle timeout range: **4–120** minutes · default: **4**.

**Q34.** **b)** Add addresses to the NAT gateway (or attach a public IP
prefix) — each address adds ~64k SNAT ports to the pool. Resizing VMs
is not the lever, and d) is impossible: a subnet takes one NAT gateway.

**Q35.** **c)** At most one NAT gateway per subnet; one gateway can
serve many subnets of the same VNet (it cannot span VNets). Once
attached it takes precedence over every other outbound method on the
subnet — LB outbound rules and instance-level public IPs are bypassed
for outbound flows.

**Q36.** A NAT gateway is outbound-only: it never accepts an unsolicited
inbound flow, so it is not an inbound exposure and needs no NSG for
that purpose. The only traffic that comes back in is return traffic on
established outbound flows.

### Section 5

**Q37.** Stuck `Initiated` → the reverse peering resource was never
created · spoke reaches hub but not other spoke → peering is
non-transitive (add direct peering, an NVA + UDR, or gateway transit) ·
UDR `Succeeded` but traffic vanishes → the NVA next hop is deallocated,
effective route state `Invalid` · new-subnet VM has no internet →
`defaultOutboundAccess` is off and no explicit outbound method exists ·
subnet creation fails → `NetcfgSubnetRangesOverlap`.

**Q38.** Lab 1's rule: VNets with overlapping address spaces can never
be peered or connected, so a collision made today forecloses topology
options forever. Lab 2's peerings program the remote VNet's whole
address space as a route, which only works when prefixes are unique;
Lab 3's UDRs steer specific remote prefixes at an NVA, which also
requires unambiguous, non-overlapping prefixes. One pre-planned /14
keeps every future peering and UDR unambiguous.

**Q39.** Prefix: **/25** — 60 + 5 reserved = 65, which does not fit a
/26 (64 addresses, 59 usable) but fits a /25 (128 addresses). Usable
addresses: **123** (2^7 − 5). A valid space: **10.103.0.0/24** or
**10.103.2.0/24** — anything inside 10.100.0.0/14 that avoids
10.100.0.0/22, 10.101.0.0/24, 10.102.0.0/24, and 10.103.1.0/24.

**Q40.** It sits at `Initiated`: the reverse resource (`hub-to-spoke3`
inside `vnet-hub`) does not exist, so the pair is incomplete and no
traffic flows. Creating the hub side flips both to `Connected`. Even
then a spoke3 VM cannot reach `vm-app1`: peering is non-transitive, so
spoke3 learns only the hub's 10.100.0.0/22 — 10.101.0.0/24 still hits
the RFC 1918 → `None` route.

**Q41.** Address prefix: **10.102.0.0/24** · next hop type:
**VirtualAppliance** · next hop IP: **10.100.2.4** · associated with
**vnet-spoke1 / snet-workload** (the route table lives in the source
subnet). Also required: `allowForwardedTraffic` on the hub↔spoke
peerings (spoke2 must accept packets the hub *forwarded*, not
originated) and `enableIPForwarding` on `vm-fw1`'s NIC — plus the OS
half, `net.ipv4.ip_forward=1`, or the kernel drops what the fabric
delivers.

**Q42.** **b)** Two failures at once. Longest prefix always wins: for
spoke2-bound traffic the RFC 1918 → `None` system route is longer than
/0, so the packets drop and R3 is broken — precedence (User > System)
never overrides prefix length. And the /0 UDR does override the system
internet route, so the entire subnet loses direct internet access
(forced tunneling through an NVA that may not be configured for it).

**Q43.** Create a **Standard SKU public IP**, create a **NAT gateway**
with that IP as its frontend (idle timeout 4 unless long-lived quiet
flows are called out), then associate the gateway with spoke3's subnet
via `az network vnet subnet update --nat-gateway`. The probe works
beforehand because `az vm run-command` rides the control plane, not the
data plane — its success proves nothing about outbound reachability.
Afterward every present and future VM in the subnet egresses from the
NAT gateway's public IP with no per-VM configuration; the VMs themselves
still have no public IP.
