## Answers

### Section 1

**Q1.** Azure's resolver fabric — there are no servers. Queries flow
through the wire server (`168.63.129.16`) in each linked VNet; the zone is
serverless name storage the platform answers for.

**Q2.** **c)** Links are the only grant. Peering moves packets, not DNS
scope — each VNet needs its own link to resolve the zone.

**Q3.** Registration links let the platform auto-create/delete VM records
in the zone; resolution links are read-only. Reading requires **either** —
all linked VNets resolve all records; the flag only governs writing.

**Q4.** 100 / 1000 / 1.

**Q5.** The auto-registered record is removed by the platform (it tracks
VM lifecycle). The static record stays — DNS asserts, it never checks;
manual records are yours to clean.

**Q6.** `false` — lowercase; az prints tsv booleans lowercase.

**Q7.** Private zone names are scoped by their VNet links, not globally
registered. Each copy answers only the VNets linked to it, so identical
names never meet.

**Q8.** `10.1.2.3` — the linked private zone takes precedence over public
DNS. Split-horizon (split-brain) DNS; the mechanism behind `privatelink.*`
private-endpoint zones.

**Q9.** ~40 A records appear without operator action — auto-registration
back-fills existing VMs; expect them within about a minute (the lab polls
rather than reads once).

**Q10.** **c)** — full record-type support (SOA managed at the apex);
private zones are real zones, minus the internet.

### Section 2

**Q11.** **SOA** (zone metadata: serial, timers, primary NS name) and
**NS** (the authoritative server set). Azure manages both at the apex;
neither can be deleted.

**Q12.** TLD-level fault isolation — an outage of one registry still
leaves three name servers resolving.

**Q13.** Delegation: the parent zone/registrar must point NS records at
the four Azure name servers. It happens at the registrar (or parent zone),
never inside Azure.

**Q14.** Lower TTL → wait out the *old* TTL (caches must expire into the
short lease) → change the record (staleness now bounded by the low TTL) →
raise TTL back.

**Q15.** One record per CNAME record set; no CNAME at the zone apex
(conflicts with the mandatory SOA/NS).

**Q16.** An Azure **resource ID** (public IP, Traffic Manager, CDN, Front
Door, or another record set in the zone). Lifecycle: auto-updates when the
target's address changes; empties itself when the target is deleted.

**Q17.** **b)** — alias-at-apex is the feature's core purpose.

**Q18.** Nothing — the record set empties (queries get no answer) instead
of serving a dead address. Designed: a wrong answer is worse than no
answer; the alias's contract is truth-tracking.

### Section 3

**Q19.** Fixed virtual IP, identical in every VNet/region; the default
VNet DNS path through which private zones (and Azure-provided resolution)
answer; unreachable from outside Azure (it also serves IMDS/host duties) —
so hybrid designs can never just "point on-prem at it."

**Q20.** The linked private zone wins — private zones are consulted before
public resolution; public DNS is only reached for names no linked zone
claims.

**Q21.** `168.63.129.16` is unreachable from outside Azure. The
**inbound endpoint** of a DNS Private Resolver provides a routable private
IP inside a VNet subnet that on-prem servers can target (conditional
forwarder for the zone's name → inbound endpoint IP).

**Q22.** The **outbound endpoint** plus a **DNS forwarding ruleset**: a
rule per domain (`corp.internal.` → on-prem DNS IPs). The ruleset is
**linked to VNets**; linked VNets' queries for matching names are
forwarded out through the outbound endpoint.

**Q23.** IaaS DNS forwarder VMs (a pair of BIND/Windows DNS boxes in the
hub forwarding both ways). The resolver removes VM patching/HA/scaling —
it is a managed, zone-redundant service priced per endpoint, not an OS you
babysit.

**Q24.** **b)** — ruleset links define scope, exactly like private-zone
links; nothing is subscription-wide or carried by peering.

**Q25.** One DNS Private Resolver in the hub VNet: an **inbound endpoint**
in a dedicated delegated subnet (gets a private IP; on-prem conditional
forwarder for `internal.example` → that IP over the VPN) and an **outbound
endpoint** in a second delegated subnet, plus a **forwarding ruleset**
(`corp.internal.` → on-prem DNS servers) linked to the hub and spoke
VNets. Private zone links keep answering the Azure side as before.
